§ 01

The mental shift

TypeScript is JavaScript with types layered on top. Internalize four facts before you start, and the rest of the language makes sense.

  1. Every valid JS file is valid TS. You can rename .js to .ts and start adding types incrementally.
  2. Types are erased at compile time. The runtime is plain JavaScript. There's no typeof at runtime in the C++ sense — the compiler checks, then strips.
  3. Typing is structural, not nominal. Two unrelated types with the same shape are interchangeable. This is the biggest C++ surprise.
  4. Inference is aggressive. Most of the time, the compiler figures out the type for you. Annotate boundaries (function params, returns, exports) — let it infer the rest.
Note on structural typing

In C++, two classes with identical members are still distinct types. In TS, they aren't. If a function takes { x: number; y: number }, it accepts any object with those fields — regardless of whether it was declared as a Point, Vec2, or an anonymous literal. This is "duck typing, but checked."

Structural typing in action
interface Point { x: number; y: number; }
interface Vec2  { x: number; y: number; }

function distance(p: Point) {
  return Math.hypot(p.x, p.y);
}

const v: Vec2 = { x: 3, y: 4 };
distance(v); // ✓ Compiles fine. Vec2 has the right shape.
§ 02

Annotations & inference

The compiler infers the type of any value initialized at declaration. Annotate at the edges of your code — function signatures, exported constants, generic parameters — and let the body type itself.

Over-annotated (avoid)
const name: string = 'Ada';
const count: number = 0;
const items: number[] = [1, 2, 3];

const total: number = items
  .reduce((sum: number, n: number): number => sum + n, 0);
Idiomatic (let TS infer)
const name = 'Ada';      // string
const count = 0;         // number
const items = [1, 2, 3]; // number[]

const total = items
  .reduce((sum, n) => sum + n, 0); // number

The exception is functions. Annotate parameters always. Annotate return types when you want the compiler to enforce a contract you might otherwise drift away from.

Annotate function boundaries
// Parameters: required. Return: optional but recommended for public APIs.
function fetchUser(id: number): Promise<User> {
  return fetch(`/api/users/${id}`).then(r => r.json());
}
§ 03

Primitives, arrays, objects

JavaScript's runtime types, plus a couple of structural extras. No int vs float vs double — there's just number.

Primitives
let s: string = 'hello';
let n: number = 42;       // covers integers AND floats — only one numeric type
let b: boolean = true;
let nothing: null = null;
let missing: undefined = undefined;
let huge: bigint = 9007199254740993n;
let sym: symbol = Symbol('id');

Arrays & tuples

Two array notations, plus tuples
let names: string[] = ['Ada', 'Linus'];
let scores: Array<number> = [98, 87];   // equivalent

// Tuples — fixed length, fixed types per slot
let pair: [string, number] = ['Ada', 30];
let rgb: readonly [number, number, number] = [255, 128, 0];

// Variadic tuples
let path: [string, ...number[]] = ['origin', 1, 2, 3];

Object types

Inline object types
let user: { name: string; age: number; admin?: boolean } = {
  name: 'Ada',
  age: 30
};

// readonly fields — like C++ const data members
let config: { readonly host: string; port: number } = {
  host: 'localhost',
  port: 8080
};
config.port = 9090;     // ✓
config.host = 'remote'; // ✗ Cannot assign to 'host' — it is readonly
§ 04

Union & literal types

The single biggest unlock when moving from JS to TS. You can express "this value is one of these specific things" without inheritance, enums, or runtime checks.

Union types
let id: string | number;
id = 'abc';   // ✓
id = 42;      // ✓
id = true;    // ✗

function format(value: string | number): string {
  return typeof value === 'string' ? value.toUpperCase() : value.toFixed(2);
}

Literal types

A type can be a single specific value. Combined with unions, you get enum-like behavior with zero runtime cost.

Literal unions replace enums
type Align = 'left' | 'right' | 'center';
type DiceRoll = 1 | 2 | 3 | 4 | 5 | 6;
type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE';

function setAlignment(a: Align) { /* ... */ }

setAlignment('left');     // ✓
setAlignment('middle');   // ✗ Argument of type '"middle"' is not assignable

Discriminated unions

The pattern that replaces most of what you'd reach for inheritance for in C++: a tag field that lets the compiler narrow the type.

Discriminated union
type Result<T> =
  | { kind: 'ok'; value: T }
  | { kind: 'error'; message: string };

function handle(r: Result<number>) {
  if (r.kind === 'ok') {
    console.log(r.value);   // TS knows r.value: number here
  } else {
    console.log(r.message); // TS knows r.message: string here
  }
}
Why this matters for your dashboard

Every API call can be modeled as Result<T> or as a union like { status: 'loading' } | { status: 'ready'; data: T } | { status: 'error'; err: Error }. The compiler then forces you to handle every state.

§ 05

Interfaces vs type aliases

Both name a type. They overlap heavily. Knowing when to reach for which is mostly stylistic — but there are a few real differences.

interface
interface User {
  name: string;
  age: number;
}

// Can be re-opened (declaration merging)
interface User {
  email: string;
}
// User now has all three fields.

// Inheritance with extends
interface Admin extends User {
  permissions: string[];
}
type alias
type User = {
  name: string;
  age: number;
};

// Cannot re-open. But can do things interfaces can't:
type ID = string | number;
type Tuple = [number, number];
type Keys = keyof User;
type Readonly<T> = { readonly [K in keyof T]: T[K] };

// Composition with intersection
type Admin = User & { permissions: string[] };
Rule of thumb

Use interface for object shapes that describe contracts (component props, API responses, class implementations). Use type for everything else — unions, intersections, primitives, mapped/conditional types. The TypeScript team uses interface by default for public-facing types because of declaration merging, but type for everything internal.

§ 06

Optional & nullable

JavaScript has two empties — null and undefined. TS lets you encode whether a field is genuinely absent (?) or present-but-nullable.

Optional vs nullable
interface User {
  name: string;
  email?: string;          // optional: may be missing entirely
  middleName: string | null; // present, but may be null
}

const a: User = { name: 'Ada', middleName: null };          // ✓
const b: User = { name: 'Ada', middleName: 'B', email: '@' }; // ✓

The four operators you'll use constantly

?. ?? ! ?:
// Optional chaining: short-circuits if nullish
const city = user?.address?.city;   // string | undefined

// Nullish coalescing: fall back if null/undefined (NOT for empty string or 0)
const port = config.port ?? 8080;

// Non-null assertion: "trust me, this is defined" — use sparingly
const el = document.getElementById('root')!;

// Compare: || falls back on ANY falsy value (0, '', false), ?? only on null/undefined
const count1 = value || 10;   // 10 if value is 0, '', false, null, or undefined
const count2 = value ?? 10;   // 10 only if value is null or undefined
Treat ! as a smell

Every ! is a promise to the compiler that you've checked something it can't see. If you're wrong, you crash at runtime. Prefer narrowing (next section) over assertions whenever possible.

§ 07

Narrowing & type guards

When a value has a union type, the compiler tracks which branch you're in based on the checks you write. This is "control-flow analysis," and it's smarter than you'd expect.

Built-in narrowing
function describe(x: string | number | string[] | Date | null) {
  if (x === null)         return 'nothing';
  if (typeof x === 'string') return x.toUpperCase();      // x: string here
  if (typeof x === 'number') return x.toFixed(2);          // x: number here
  if (Array.isArray(x))      return x.join(', ');          // x: string[] here
  if (x instanceof Date)     return x.toISOString();       // x: Date here
  // x: never here — all cases handled
}

The in operator

Narrowing by property presence
type Cat = { meow: () => void };
type Dog = { bark: () => void };

function speak(animal: Cat | Dog) {
  if ('meow' in animal) animal.meow();  // animal: Cat
  else animal.bark();                    // animal: Dog
}

User-defined type guards

When you need to narrow on something more complex, write a function that returns a type predicate (x is Foo).

Custom type guard
function isUser(value: unknown): value is User {
  return (
    typeof value === 'object' &&
    value !== null &&
    'name' in value &&
    typeof (value as any).name === 'string'
  );
}

const data: unknown = await fetch('/api/me').then(r => r.json());
if (isUser(data)) {
  console.log(data.name);  // data: User here
}
§ 08

Generics

If you remember C++ templates, you already know 80% of TypeScript generics. The syntax differs but the idea is the same: parameterize a function, class, or type by another type.

Basic generic function
function identity<T>(value: T): T {
  return value;
}

const a = identity(42);       // T inferred as number
const b = identity('hello');  // T inferred as string
const c = identity<boolean>(true); // T explicit

Constraints — the equivalent of std::enable_if

Generic with constraint
// Constrain T to anything with a length property
function logLength<T extends { length: number }>(x: T): T {
  console.log(x.length);
  return x;
}

logLength('hello');         // ✓ string has length
logLength([1, 2, 3]);       // ✓ array has length
logLength(42);              // ✗ number does not have length

Generics in interfaces and types

Generic types
interface ApiResponse<T> {
  data: T;
  status: number;
  timestamp: Date;
}

type Pair<A, B = A> = [A, B]; // B defaults to A

const userResp: ApiResponse<User> = {
  data: { name: 'Ada', age: 30 },
  status: 200,
  timestamp: new Date()
};
Note vs templates

Two big differences from C++ templates: (1) TS generics are checked once at definition, not instantiated per use, so you can't do C++-style template metaprogramming with overload resolution tricks. (2) TS has conditional types (T extends U ? X : Y) which are roughly the equivalent of SFINAE / if constexpr, and they're a lot more readable. You won't need them for a dashboard, but they're there.

§ 09

Utility types

Built-in generic types that transform other types. The ones you'll use weekly:

Object transformations
interface User { id: number; name: string; email: string; admin: boolean; }

type PartialUser  = Partial<User>;   // every field optional
type RequiredUser = Required<User>;  // every field required (strips ?)
type FrozenUser   = Readonly<User>;  // every field readonly

type PublicUser = Pick<User, 'id' | 'name'>;
//   { id: number; name: string }

type SafeUser = Omit<User, 'admin'>;
//   { id: number; name: string; email: string }
Record & function-related
// Record: build an object type from key union and value type
type CpuTemps = Record<'core0' | 'core1' | 'core2' | 'core3', number>;
//  { core0: number; core1: number; core2: number; core3: number }

type StatusColors = Record<'ok' | 'warn' | 'error', string>;

// Function-related
function greet(name: string, formal: boolean): string { return ''; }

type GreetParams = Parameters<typeof greet>;  // [name: string, formal: boolean]
type GreetReturn = ReturnType<typeof greet>;  // string

// Promise unwrapping
type UserData = Awaited<ReturnType<typeof fetchUser>>; // unwraps Promise<User>
§ 10

unknown / any / never

Three types that look weird and behave differently. Knowing which is which prevents most TS-related foot-shooting.

any — the escape hatch

Disables all type checking for that value. Anything goes. Avoid it. Every any is a hole in your type safety. If you find yourself reaching for it, reach for unknown first.

unknown — the safe top type

Like any, but the compiler forces you to narrow it before doing anything. Perfect for values from outside your program: JSON.parse results, fetch responses, third-party callbacks.

unknown forces narrowing
const raw: unknown = JSON.parse(text);

raw.toUpperCase();     // ✗ Object is of type 'unknown'

if (typeof raw === 'string') {
  raw.toUpperCase();   // ✓ narrowed to string
}

never — the bottom type

The type of values that cannot exist. Useful for exhaustiveness checks and functions that don't return.

Exhaustiveness check
type Shape = { kind: 'circle'; r: number } | { kind: 'square'; side: number };

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'square': return s.side ** 2;
    default: {
      const _exhaustive: never = s; // ✗ if you add a new shape and forget here
      return _exhaustive;
    }
  }
}

// Functions that throw or loop forever return 'never'
function fail(msg: string): never { throw new Error(msg); }
§ 11

Assertions: as, as const, satisfies

Three different ways to tell the compiler something about a value's type. Each does something subtly different — and satisfies is the newest and most often what you actually want.

as Foo — type assertion

"Trust me, treat this as Foo." No runtime check. Use only when you know more than the compiler does.

Type assertion
const input = document.getElementById('email') as HTMLInputElement;
input.value = 'hi';  // OK — without `as`, TS sees HTMLElement | null

as const — literal narrowing

Tells the compiler "treat every value here as its most specific literal." Without it, TS widens. Useful for config objects and arrays.

as const narrows literals
const colors1 = ['red', 'green', 'blue'];
//    colors1: string[]

const colors2 = ['red', 'green', 'blue'] as const;
//    colors2: readonly ['red', 'green', 'blue']

type Color = typeof colors2[number]; // 'red' | 'green' | 'blue'

satisfies — validate without widening

The newest of the three (TS 4.9+). Says "check that this value matches the type, but keep its more specific inferred type."

satisfies in practice
type Routes = Record<string, { path: string; auth: boolean }>;

// With `: Routes` — you lose the specific keys
const routesA: Routes = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true }
};
routesA.home;     // type: { path: string; auth: boolean } | undefined

// With `satisfies Routes` — checked, but specific keys preserved
const routesB = {
  home: { path: '/', auth: false },
  admin: { path: '/admin', auth: true }
} satisfies Routes;
routesB.home;     // type: { path: string; auth: boolean } — guaranteed present
routesB.unknown;  // ✗ Property does not exist
§ 12

Function types

Function signatures get richer in TS — optional params, defaults, rest args, and named function-type aliases.

Function basics
// Required, optional, default
function greet(name: string, title?: string, greeting = 'Hello'): string {
  return `${greeting}, ${title ?? ''} ${name}`.trim();
}

// Rest parameters
function sum(...nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}

// Function type alias — like a typedef for a function pointer in C
type Comparator<T> = (a: T, b: T) => number;

const byLength: Comparator<string> = (a, b) => a.length - b.length;

// Async functions return Promise<T>
async function loadUser(id: number): Promise<User> {
  const r = await fetch(`/users/${id}`);
  return r.json();
}
Note on overloading

TS does support function overloads, but the syntax is awkward and 95% of the time, a union type or generic does the job better. Don't reach for overloads unless you've genuinely exhausted the alternatives.

§ 13

Modules & type-only imports

No headers, no #include — just ES modules. The wrinkle is that some imports are values (functions, classes) and some are types (interfaces, type aliases).

Imports & exports
// types.ts
export interface User { id: number; name: string; }
export type ID = string | number;

// utils.ts
export function formatId(id: ID): string { return String(id); }
export const MAX_USERS = 100;

// app.ts
import { formatId, MAX_USERS } from './utils';
import type { User, ID } from './types';   // erased at compile time
import { type User, formatId } from './mixed'; // mixed value/type

export type { User };
export { formatId };
Why import type matters

Bundlers can drop type-only imports entirely from the output. If you import something only for its type, mark it. This avoids accidental circular dependencies and produces leaner builds — relevant for any Tauri/SvelteKit app where bundle size matters.

§ 14

Mental model summary

The whole shift, in one table. Pin it next to the Svelte sheet.

Concept JavaScript TypeScript
Variable typing let x = 0 (any-ish) let x = 0 (inferred number)
Function params untyped (x: string, y: number)
"One of these" runtime checks 'a' | 'b' | 'c'
Object shapes by convention interface / type
Optional fields obj.foo may be undefined foo?: T or T | null
Generic container Array Array<T> / T[]
Templates — function f<T>(x: T)
Enum-like values string constants literal unions
External JSON JSON.parse → any JSON.parse → unknown, then narrow
Null guard if (x && x.foo) x?.foo
Default value x || 'default' x ?? 'default'
Type-only import — import type { Foo } from './x'

Three rules to keep you out of trouble

i.

Annotate boundaries, infer the middle. Function parameters, exports, and public API surfaces get explicit types. Local variables get inferred types. Over-annotating obscures real errors.

ii.

Reach for unions before classes, hierarchies, or any. Most "polymorphism" problems in JS are better expressed as discriminated unions than as inheritance trees.

iii.

Treat any and ! as smells. Both silence the compiler. Use unknown + narrowing instead. If you genuinely need an escape hatch, leave a comment explaining why.
